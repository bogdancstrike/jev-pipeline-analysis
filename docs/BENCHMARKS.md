# Benchmarks

All numbers measured on the actual deployment: **one RTX 3080 (10 GB)** that also drives a
desktop, Ryzen/32 threads, 60 GB RAM, the compose stack of this repo (GLiNER2.5 extractor +
Laya, bf16). Data: `samples/sample-*.csv`, synthetic news of **300–1,500 words** (median ~675)
in 7 languages, generated by `scripts/generate_sample.py` with ground-truth columns
(`gold_event`, `gold_topic`, `story`). Reproduce with `scripts/benchmark.py`; raw JSON lands in
`benchmarks/runs/` (git-ignored).

> Measure on a quiet machine: another job, or a desktop on the same GPU, skews results.
> Synthetic bodies are topic-generic filler, so accuracy numbers favour reading the lead; real
> inverted-pyramid news behaves the same way, less strongly.

## Tuning experiments (what changed, and why)

Accuracy is measured against the gold columns on 100 labelled articles.

**Topic (GLiNER2.5-Decide)**

| Setting | Articles/s | Accuracy |
|---|---:|---:|
| whole text, labels + descriptions (old default) | 8.0 | 29% |
| lead 3,000 chars | 11.9 | 32% |
| **lead 1,500 chars, label names only (new default)** | **46.0** | **62%** |
| lead 1,500 chars, labels + descriptions | 26.2 | 50% |
| Laya, lead, max_len 1,024 | 51.1 | 64% |

**Event type (Laya), by context length**

| max_len | Articles/s | Accuracy |
|---:|---:|---:|
| 2,048 (old) | 24.8 | 75% |
| **1,024 (new, with the same for relevance, risk, intent, toxicity)** | **48.0** | **78%** |
| 512 | 87.6 | 72% |

Agreement with 2,048 at 1,024 tokens (no gold for these): relevance 96%, risk/intent/toxicity
92%, sentiment 88%, routing 75%, propaganda 62%. Routing, sentiment and propaganda therefore
stay at 2,048 (quality first).

**Laya, several questions in one request**: no gain (×1.0); Laya re-encodes document +
question per question. Not used.

**Entities, label set**: 13 distinct labels vs the old 20 — same speed (+5%), **22% more**
people/places/organizations found (near-duplicate labels split the score), 95% of the old
set's spans kept. New default: 13.

**Structured fields, lead**: 2,500 chars is 1.6× faster with 92% identical "what"
(1,500 chars: 3.8× faster but only 52% identical). New default: 2,500.

**Extractor**: smaller inner batches are faster on long documents (bs 8 ≈ 21/s vs bs 32
≈ 15/s: padding); `disentangled_flash` attention gave no measurable gain on this card.

## Scale (backend overhead)

`pytest -m scale` — 50,000 articles (260 MB) through the real scheduler and CPU modules with
instant fake engines: parse 1.3 s, **643 rows/s** for 6 tasks (over 100× GPU speed, so overhead
is negligible), summary 0.15 s, snapshot < 1 ms, CSV export 4.2 s (490 MB). No quadratic path.

## Bugs found by benchmarking

* **Laya CPU fallback**: the extractor's memory cache could grow into Laya's share; Laya then
  moves a checkpoint to the CPU and keeps serving ~30× slower. Fixed by memory budgets
  (extractor 35% + cache release, Laya batch token cap) and surfaced as "degraded" health.
* **Extractor OOM retries** wasted forward passes: sticky per-task batch caps.
* **Records completed only at the end**: tasks sharing an engine are now kept row-aligned.

## Estimates for bigger runs (tuned, all 15 tasks)

At 2.5 articles/s: 5,000 articles ≈ 33 min, 30,000 ≈ 3.3 h, 50,000 ≈ 5.5 h. The Fast
preset (11 tasks) runs faster still; Language + Entities + Resolution alone ≈ 20 articles/s
(50,000 in ≈ 42 min).
